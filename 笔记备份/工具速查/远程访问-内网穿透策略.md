# 远程访问-内网穿透策略

> 用途：把“没有公网 IP，怎么让外网访问内网服务”讲清楚：反向隧道、HTTP 反代、P2P 打洞、TURN/Relay。
> 配套：总览与选型见 [[somezhishi/工具速查/远程访问-内网穿透与虚拟组网|远程访问：内网穿透与虚拟组网]]；反向 SSH 实操见 [[somezhishi/工具速查/内网穿透-反向SSH远程WSL|内网穿透：反向 SSH 远程 WSL]]。
> 结论先行：**内网穿透不是一种协议，而是一类“让内网服务可达”的方案；典型代表是反向隧道，P2P 打洞和中继是另外两条路。**

## 一、反向端口映射 / 反向隧道

```text
内网服务 <内网IP>:8080
   ↑
frpc / ngrok agent / ssh -R
   │ 主动出站连接
   ↓
公网服务器 frps / ngrok edge / VPS
   │ 监听公网端口 8080
   ↓
互联网用户 → 公网服务器:8080 → 隧道 → 内网服务
```

内网主机主动向公网服务器建立长连接，公网服务器在某个端口上接收外部请求，再通过这条连接转发给内网。

**为什么叫“反向”：**

普通访问是“外面连进来”；NAT 后面的机器没有公网入口，只能反过来——由内网机器先连出去，在公网服务器上开一个“口子”。

**常见实现：**

- **frp**：自建 `frps` + `frpc`，支持 TCP/UDP/HTTP/HTTPS、多路复用、加密、压缩、鉴权、Dashboard。
- **nps**：类似 frp，带 Web 管理界面。
- **ngrok**：SaaS，一条命令暴露本地端口；免费版有域名/带宽限制。
- **cloudflared**：Cloudflare Tunnel，出站连接到 Cloudflare 边缘，绑定域名；常配 Cloudflare Access 做 SSO。
- **rathole / sish / boringproxy**：轻量自建替代。
- **`ssh -R`**：最原始的反向隧道，VPS 上 `GatewayPorts` 开端口；配 `autossh`/systemd 保活。

**优点：**

- 对网络环境要求最低：只要能出站上网即可，CGNAT、双层 NAT、公司防火墙都能用。
- 不需要改路由器、不需要公网 IP、不需要 DDNS。
- 可以暴露任意 TCP/UDP/HTTP 服务。
- frp/nps 可自建，可控；ngrok/cloudflared 开箱即用。
- 适合 Webhook、开发联调、远程 SSH、NAS、监控、演示。

**缺点：**

- **所有流量都走公网服务器**：带宽、延迟、流量成本都受服务器限制。
- 公网服务器是**单点故障**和**攻击面**；需要做好防火墙、鉴权、TLS、日志。
- 如果服务器终止 TLS，服务器能看到明文；要端到端加密需应用层再加密。
- 端口管理麻烦：多个服务要分配端口/域名。
- 免费 SaaS 有带宽、连接数、域名、休眠限制。
- 不适合大流量、低延迟、长期高吞吐场景。

**适用：** 家里/公司没有公网 IP，但有一个 VPS；只想暴露一两个 Web 服务或 SSH；临时开发、演示、远程支持。

> [!warning] 安全底线
> 不要把 RDP、数据库、SSH 直接裸奔到公网。至少加：强密码/密钥、MFA、TLS、IP 白名单、fail2ban、只暴露必要端口。

## 二、HTTP/HTTPS 反向代理型穿透

```text
浏览器 → https://app.example.com
          → Cloudflare / nginx / Caddy（公网）
            → tunnel → 内网 localhost:3000
```

这是反向隧道的一种“Web 友好”变体：

- 公网侧只开 80/443，按域名/Host/Path 路由。
- 自动 TLS 证书、WebSocket、HTTP/2、HTTP/3。
- 常和 SSO/访问策略结合（Cloudflare Access、OAuth2 Proxy、Authelia）。
- 比“暴露一个 TCP 端口”更安全、更好管理。

**代表：** Cloudflare Tunnel、ngrok HTTP、frp HTTP 模式、Caddy + 反向隧道、Tailscale Funnel/Serve。

**优点：** 只开 443、容易加认证、支持多域名、自动证书、对防火墙友好。  
**缺点：** 主要适合 HTTP(S)；TCP/UDP 需要额外方案；SaaS 会看到 TLS 终止后的明文（除非应用层 E2EE）。

## 三、P2P NAT 穿越（打洞）

这不是“端口映射”，而是让两端**直接建立连接**，不经过业务中继。

**核心组件：**

- **信令服务器**：交换双方的候选地址、SDP、公钥等。
- **STUN**：告诉客户端“你在公网看起来是什么 IP:端口”。
- **ICE**：收集候选地址（host、srflx、relay），逐一测试连通性，选最优路径。
- **TURN**：打洞失败时的中继兜底。
- **UDP/TCP hole punching**：双方同时向对方公网地址发包，让 NAT 建立映射。

**NAT 类型与打洞难度：**

| NAT 类型 | 行为 | 打洞难度 |
|---|---|---|
| Full Cone | 内部主机出站后，任何外部主机都可发入 | 容易 |
| Restricted Cone | 只允许已通信过的外部 IP 发入 | 较易 |
| Port-Restricted Cone | 只允许已通信过的外部 IP:端口发入 | 中等 |
| Symmetric NAT | 每个目标分配不同公网端口，外部无法预知 | 难，通常要 TURN |

再加上 **CGNAT、双层 NAT、企业防火墙、UDP 被封**，P2P 成功率会明显下降。所以成熟方案一定是 **P2P 优先 + 中继兜底**，不会承诺 100% 打洞成功。

**优点：**

- 延迟最低，路径最短。
- 不消耗中继带宽，成本低。
- 隐私更好：数据不经过业务服务器（信令除外）。
- 适合实时音视频、远程桌面、游戏、文件传输。

**缺点：**

- NAT/防火墙行为不可控，失败率高。
- 需要 STUN/TURN/信令基础设施。
- UDP 可能被封；TCP 打洞兼容性更差。
- 移动网络切换、NAT 映射超时会导致连接中断，需要重连。
- 直连会暴露双方 IP（隐私/风控），需要 E2EE。

**代表：** WebRTC、Parsec、Moonlight、Tailscale/ZeroTier 的 P2P 路径、DSH Remote。

## 四、中继转发（TURN / DERP / WebSocket Relay）

当 P2P 失败时，流量经公网服务器转发：

- **TURN**：WebRTC 标准中继，支持 UDP/TCP/TLS；服务器分配 relay 地址，转发媒体/数据。
- **DERP**：Tailscale 的中继，走 HTTPS/WebSocket，转发 WireGuard 密文，穿透防火墙友好。
- **WebSocket Relay**：应用层中继，DSH Remote 的最终兜底；服务端只转发密文。
- **frp/ngrok**：本质上也是中继，只是更偏“端口映射”。

**优点：** 成功率高，几乎一定能连；适合严格网络。  
**缺点：** 增加延迟、消耗服务器带宽、成本高；服务器能看到流量元数据（E2EE 时看不到明文）。

**结论：** 现代远程访问的标配是 **P2P 优先 + 中继兜底**，而不是二选一。

## 五、怎么选

| 场景 | 推荐 | 理由 |
|---|---|---|
| 有公网 VPS，想暴露多个 TCP 服务 | frp / nps | 自建、可控、支持任意 TCP/UDP |
| 只想临时暴露本地 Web 服务 | Cloudflare Tunnel / ngrok | 一条命令、自动 TLS、可加 SSO |
| 有公网 VPS，只想临时 SSH | `ssh -R` + autossh | 不用装额外软件 |
| 低延迟远程桌面/游戏 | P2P（WebRTC/Parsec/Moonlight）+ TURN | 直连延迟最低 |
| 严格防火墙、UDP 被封 | TURN over TCP/TLS 或 WebSocket Relay | 走 443，成功率最高 |
| 企业只开放单个应用 | ZTNA | 最小权限、审计、SSO |

## 术语小词典

| 术语 | 大白话 |
|---|---|
| 反向隧道 | 由内网机器主动拨出到公网机器，并在对方机器上开一个转发口 |
| NAT | 把私有 IP/端口翻译成公网 IP/端口 |
| NAT 穿透 | 让 NAT 后的设备直接建立连接；不是“组网” |
| STUN | 查“我在公网长什么样”，不转发数据 |
| TURN | 打洞失败时的中继服务器，流量经它转发 |
| ICE | 收集候选地址、测试连通性、选最优路径 |
| Hole punching | 双方同时向对方公网地址发包，让 NAT 建立映射 |
| CGNAT | 运营商级 NAT；很多手机/宽带没有独立公网 IP |
| DERP | Tailscale 的中继，走 HTTPS/WebSocket，转发 WireGuard 密文 |

> [!question]- 自测
> 1. 为什么叫“反向”隧道？
> 2. STUN 和 TURN 的区别是什么？
> 3. 为什么 P2P 打洞不能保证 100% 成功？
> 4. 什么情况下应该直接上中继？
>
> 答案：1. 因为由内网机器主动连公网服务器，在公网服务器上开一个口子；方向和“外面连进来”相反。2. STUN 只告诉客户端公网映射，不转发数据；TURN 是真正的中继，流量经它转发。3. NAT 类型（symmetric）、CGNAT、双层 NAT、防火墙封 UDP 都会让打洞失败。4. 双方都在 symmetric NAT/CGNAT 后、UDP 被封、或要求稳定优先于延迟时。
